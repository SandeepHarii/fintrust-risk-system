FinTrust

A cloud-based transaction insights and risk monitoring system designed around a banking scenario. It automates transaction ingestion, validation, and risk detection while giving compliance teams visibility into potentially suspicious activity.

AWS · eu-north-1 Serverless · Event-driven POPIA-informed design Cloud · SQL · Python · Governance

Presented by Sandeep Hari · 19–20 October 2026

01 · BUSINESS PROBLEM

Manual transaction review doesn't scale

In a banking environment, transaction exports need to be processed consistently and reviewed for potential risk. When this depends heavily on manual checks, validation, investigation, and reporting become harder to manage.

The challenge

Manual processing

Transaction data arrives in flat files. Analysts need to inspect records, identify suspicious activity, and organise information for further investigation.

Business impact

Inconsistent visibility

Manual checks can be difficult to repeat and audit. Without structured validation and recorded rule outcomes, it is harder to trace why a transaction was flagged.

The requirement

Automate the transaction flow

Build an event-driven system that validates transactions, applies risk rules, stores results, exposes a secure REST API, and produces alerts and monthly reports.

The goal is to support compliance and fraud teams with more consistent information. The system supports investigation; it does not replace analyst judgement.

02 · SOLUTION

An event-driven serverless platform

CSV uploads move through validation, asynchronous processing, risk scoring, and persistence. Results are made available to compliance through an API, dashboard, alerts, and reporting.

Ingest

CSV to S3

The upload endpoint stores the incoming file in the S3 raw area. The ingest Lambda validates and sanitises transaction rows. Invalid records are sent to quarantine.

Process

Queue and score

Step Functions orchestrates the upload workflow and tracks its execution. Valid records are placed on SQS FIFO, which decouples ingestion from scoring. The score Lambda applies the configured HIGH_AMOUNT, HIGH_VELOCITY, and CROSS_BORDER rules.

Store

RDS + DynamoDB

RDS PostgreSQL stores the structured transaction ledger. DynamoDB supports key-based access to risk scores and transaction events.

Serve

API, alerts, reports

API Gateway exposes the query API. SES supports email alerts for HIGH-risk results. EventBridge schedules the monthly reporting Lambda.

Why asynchronous processing?

Loose coupling

The upload request does not need to wait for every transaction to be scored and stored. Step Functions coordinates the upload workflow, while SQS separates ingestion from scoring. Each stage can process work independently, helping absorb bursts of incoming transactions without requiring the upload endpoint to perform all processing at once.

Important API behaviour

HTTP 202 means accepted

The upload endpoint acknowledges that processing has been accepted. The dashboard checks backend processing status. It only shows completion after the records have been persisted. This separates a successful upload acknowledgement from successful completion of the processing workflow.

03 · CLOUD ARCHITECTURE

The AWS services behind the system

Each service has a specific responsibility. Together, they provide storage, processing, communication, security, and monitoring.

Storage and databases

Where the data lives

  • Amazon S3: Object storage for uploaded CSVs, processed data, quarantine records, and reports.
  • Amazon RDS: Managed PostgreSQL database for the structured transaction ledger.
  • Amazon DynamoDB: NoSQL database for fast key-based access to risk data and events.
  • S3 Glacier storage classes: Lower-cost archival options within S3 for data that needs longer-term storage.

Processing and integration

How work moves

  • AWS Lambda: Runs application code when an event or request triggers it.
  • AWS Step Functions: Orchestrates the upload workflow and tracks execution across processing steps.
  • Amazon SQS FIFO: Separates ingestion from scoring and supports ordered processing within message groups.
  • Dead-letter queue: Isolates messages that repeatedly fail processing so they can be inspected.
  • API Gateway: The controlled front door for the REST API, including API key and usage-plan controls.
  • EventBridge: Triggers scheduled work, including monthly reporting.

Security and operations

How the system is controlled

  • IAM: Controls which users and services can perform specific actions.
  • VPC: Provides the network boundary for private resources such as RDS.
  • VPC endpoints: Provide private connectivity to supported AWS services without routing through a NAT Gateway.
  • SSM Parameter Store: Stores application configuration and protected parameters.
  • CloudWatch: Collects logs, metrics, and alarms.
  • X-Ray: Helps trace requests across supported application components.
  • SES: Sends email notifications.

Relational database

Why RDS PostgreSQL?

PostgreSQL stores the structured transaction ledger and its relationships. Customers, accounts, transactions, risk events, and alerts can be queried together using SQL. Relational constraints help maintain data integrity, while SQL supports reporting, investigation, and audit queries.

NoSQL database

Why DynamoDB?

DynamoDB complements PostgreSQL by supporting fast key-based access to risk scores and transaction event information. It is suited to predictable lookup patterns where an item can be retrieved directly using its key, rather than performing relational joins across the transaction ledger.

A useful distinction: API Gateway and Lambda provide the deployed AWS query API. FastAPI, SQLAlchemy, and Python are application technologies used in the project. PostgreSQL is the database engine managed through Amazon RDS.

05 · KEY FUNCTIONALITIES

What the user can do

Upload and ingest

CSV upload

Upload a transaction CSV through the dashboard. The backend accepts the request, stores the file, and starts asynchronous processing.

Data quality

Validation and quarantine

The ingestion process checks incoming records, validates required fields and data types, sanitises values, and separates invalid rows so they can be investigated or corrected.

Risk scoring

Explainable classifications

Transactions are checked against three named rules. The resulting classification and rule flags provide a traceable explanation for the risk outcome.

Compliance view

Live dashboard

The Overview screen provides a system-level summary, including transaction activity and risk distribution. Risk Monitoring provides a more detailed view of transactions and their classifications for investigation.

Alerting

Automated notifications

The alerting component sends an SES email when a transaction meets the HIGH-risk notification condition, subject to the configured email environment.

Reporting

Monthly analytics

The reporting component uses SQL analytics and an EventBridge schedule to generate monthly CSV and JSON report outputs in S3. These reports provide a consolidated view of transaction activity and risk information over the reporting period.

Initial risk rules

HIGH_AMOUNT

Transaction amount greater than R50,000.

HIGH_VELOCITY

More than 10 transactions within one hour.

CROSS_BORDER

Transaction meets the configured cross-border condition.

Example risk scenario

A R51,000 transaction

Consider a customer making a R51,000 purchase. Because the transaction exceeds the configured R50,000 threshold, the HIGH_AMOUNT rule is triggered. FinTrust records the rule outcome alongside the transaction, making the reason for the flag visible to compliance users. The transaction is highlighted for investigation rather than automatically treated as fraud.

06 · FOUR PILLARS

Four pillars, one coherent system

The project brings together four learning streams. Each pillar contributes a different part of the solution, from the cloud infrastructure to the way transaction data is managed.

Pillar 1 · Cloud

AWS Architecture

Serverless and event-driven architecture using AWS services selected for resilience, security, performance, and cost. Includes IAM, VPC networking, queues, workflow orchestration, monitoring, storage, and API integration.

Pillar 2 · SQL

Data Modelling

A relational schema designed around customers, accounts, transactions, risk events, and alerts. Includes normalisation, constraints, indexes, relationships, and analytical queries.

Pillar 3 · Python

Application Development

A ten-module Python package covering configuration, database access, DynamoDB, models, validation, ingestion, scoring, alerting, querying, and reporting.

Pillar 4 · Data Management & Governance

Data Governance

POPIA-informed data classification, data quality, lifecycle management, migration strategy, and a governance risk register with proposed controls. This pillar addresses how information is collected, validated, protected, retained, and used responsibly throughout the system.

Networking decision

Why no NAT Gateway?

The architecture excludes a NAT Gateway to avoid its hourly and data-processing charges. RDS remains in private subnets. Lambda functions that require database access connect through the VPC with security-group rules restricted to the required database port and destination.

Private AWS connectivity

VPC endpoints

VPC endpoints provide private paths to supported AWS services, including S3, SSM, and SQS. This reduces the need for public internet routing for those service interactions.

07 · DATA FLOW

Upload to alert, in six stages

01 · Upload

API Gateway, S3 and Step Functions

The upload endpoint accepts the request and stores the CSV in the raw S3 area. Step Functions coordinates the upload workflow and tracks its execution. The API responds with HTTP 202 Accepted while processing continues.

02 · Ingest

ingest.py

The ingestion Lambda reads the file, validates and sanitises rows, and sends invalid records to the quarantine area. Valid records continue to the processing queue.

03 · Queue

SQS FIFO

Valid transactions are sent to the FIFO queue. Message groups support ordered processing for the configured account key. A dead-letter queue provides a failure-isolation path for messages that repeatedly fail processing.

04 · Score

score.py

The scoring Lambda consumes queued records and applies the three configured risk rules to produce a risk result. The result includes the applicable rule flags, supporting traceability of the classification.

05 · Store

RDS + DynamoDB

Transaction records are persisted in PostgreSQL. Risk scores and event information are written to DynamoDB for the configured key-based lookup patterns. The two databases serve complementary access requirements.

06 · Alert

alert.py and SES

The alerting component evaluates the risk result and sends the configured email notification for HIGH-risk activity. This gives the relevant users an additional notification channel alongside the dashboard.

Query path

API Gateway → query.py

API Gateway routes supported REST requests to the query Lambda. The handler retrieves information from the database layer and returns the API response to the dashboard or API consumer. This path supports transaction lookup and the dashboard's data views.

Reporting path

EventBridge → report.py → S3

EventBridge triggers the monthly reporting Lambda. The reporting process runs the required SQL analytics and writes the generated report files to S3. This separates scheduled reporting from the real-time transaction processing path.

Step Functions coordinates the upload workflow. SQS is the boundary between ingestion and scoring. Messages that repeatedly fail can be isolated through the configured dead-letter queue for investigation and controlled recovery.

Backend processing

From upload to persisted results

  • File received: The uploaded CSV is stored in the raw S3 area.
  • Processing started: Step Functions coordinates the upload workflow.
  • Data validation: Valid records continue while invalid records are separated into quarantine.
  • Transactions queued: Valid transactions are passed to SQS FIFO for asynchronous processing.
  • Risk assessment: The scoring component applies the configured risk rules.
  • Results saved: Transaction and risk information is persisted in the relevant databases.

Processing visibility and reliability

Accepted, processed, and persisted are different states

The HTTP 202 response confirms that the upload request has been accepted for processing. It does not mean that every transaction has already been scored or saved. The dashboard obtains processing status from the backend, allowing progress to reflect the actual workflow. Completion is represented only after the results have been persisted.

CloudWatch logs and metrics provide operational visibility into the Lambda processing components, while Step Functions and SQS help coordinate the workflow and separate transaction ingestion from scoring. The API, database records, and generated reports provide additional views of the system's outputs.

09 · GOVERNANCE & COST

Governance, security, and cost awareness

FinTrust considers how transaction data is protected, managed, retained, and processed responsibly while keeping AWS costs under control.

Data governance

POPIA-informed design

  • Identifies personal, operational, and derived transaction information.
  • Uses validation and quarantine to manage data quality.
  • Applies access restrictions to sensitive resources.
  • Considers data lifecycle and retention requirements.

Security controls

Protecting the environment

  • IAM: Restricts access through scoped permissions.
  • SSM: Stores application configuration and protected parameters.
  • VPC: Keeps RDS within private networking.
  • VPC endpoints: Provide private access to supported AWS services.

Cost management

Avoiding unnecessary costs

  • No NAT Gateway, avoiding its hourly and data-processing charges.
  • Uses managed and serverless services where appropriate.
  • Considers AWS Free Tier allowances and available credits.
  • Billing and Cost Explorer support usage monitoring.

Data lifecycle

Proposed retention periods

  • Hot: RDS operational data for 12 months.
  • Warm: S3 storage for 3 years.
  • Cold: S3 Glacier archival for 7 years.

These are proposed design periods. Final retention must be confirmed against applicable legal and organisational requirements.

Migration strategy

Planning for legacy systems

The project evaluates AWS's 7 Rs migration strategies: Retire, Retain, Rehost, Relocate, Repurchase, Replatform, and Refactor.

AWS Application Migration Service is considered for suitable server-based workloads. Transaction files follow the S3 ingestion and processing workflow.

The focus is on responsible data handling, controlled access, private connectivity, and awareness of ongoing AWS consumption.
