01 · BUSINESS PROBLEM

Manual transaction review doesn't scale

FinTrust's operations team receives transaction exports that must be processed consistently and reviewed for risk. A manual process makes validation, investigation, and reporting harder to manage.

The challenge

Manual processing

Transaction data arrives in flat files. Analysts need to inspect records, identify suspicious activity, and organise information for further investigation.

Business impact

Inconsistent visibility

Manual checks can be difficult to repeat and audit. Without structured validation and recorded rule outcomes, it is harder to trace why a transaction was flagged.

The brief

Automate the transaction flow

Build an event-driven system that validates transactions, applies risk rules, stores results, exposes a secure REST API, and produces alerts and monthly reports.

The goal is to support compliance and fraud teams with more consistent information. The system supports investigation; it does not replace analyst judgement.

02 · SOLUTION

An event-driven serverless platform

CSV uploads move through validation, asynchronous processing, risk scoring, and persistence. Results are made available to compliance through an API, dashboard, alerts, and reporting.

Ingest

CSV to S3

The upload endpoint stores the incoming file in the S3 raw area. The ingest Lambda validates and sanitises transaction rows. Invalid records are sent to quarantine.

Process

Queue and score

Valid records are placed on SQS FIFO. The score Lambda processes queued records and applies the configured HIGH_AMOUNT, HIGH_VELOCITY, and CROSS_BORDER rules.

Store

RDS + DynamoDB

RDS PostgreSQL stores the structured transaction ledger. DynamoDB supports key-based access to risk scores and transaction events.

Serve

API, alerts, reports

API Gateway exposes the query API. SES supports email alerts for HIGH-risk results. EventBridge schedules the monthly reporting Lambda.

Why asynchronous processing?

Loose coupling

The upload request does not need to wait for every transaction to be scored and stored. SQS separates ingestion from scoring, allowing each stage to process work independently.

Important API behaviour

HTTP 202 means accepted

The upload endpoint acknowledges that processing has been accepted. The dashboard checks backend processing status. It only shows completion after the records have been persisted.

03 · CLOUD ARCHITECTURE

The AWS services behind the system

Each service has a specific responsibility. Together, they provide storage, processing, communication, security, and monitoring.

Storage and databases

Where the data lives

  • Amazon S3: Object storage for uploaded CSVs, processed data, quarantine records, and reports.
  • Amazon RDS: Managed PostgreSQL database for the structured transaction ledger.
  • Amazon DynamoDB: NoSQL key-value/document database for fast access to risk data and events.
  • S3 Glacier storage classes: Lower-cost archival storage options within S3, not a separate database.

Processing and integration

How work moves

  • AWS Lambda: Runs application code when an event or request triggers it.
  • Amazon SQS FIFO: A message queue that separates ingestion from scoring and supports ordered processing within message groups.
  • Dead-letter queue: A separate SQS queue for messages that repeatedly fail processing.
  • API Gateway: The controlled front door for the REST API.
  • EventBridge: Routes events and triggers scheduled work, such as monthly reporting.

Security and operations

How the system is controlled

  • IAM: Controls which users and services can perform specific actions.
  • VPC: Provides the network boundary for private resources such as RDS.
  • VPC endpoints: Provide private connectivity to supported AWS services without routing through a NAT Gateway.
  • SSM Parameter Store: Stores application configuration and protected parameters.
  • CloudWatch: Collects logs, metrics, and alarms.
  • X-Ray: Helps trace requests across supported application components.
  • SES: Sends email notifications.

A useful distinction: API Gateway and Lambda provide the deployed AWS query API. FastAPI, SQLAlchemy, and Python are application technologies used in the project. They are not AWS services.

Criterion 5 · 10 marks

Networking decision

Why no NAT Gateway?

The architecture excludes a NAT Gateway to avoid its hourly and data-processing charges. RDS remains in private subnets. Lambda functions that require database access connect through the VPC with security-group rules restricted to the required database port and destination.

Private AWS connectivity

VPC endpoints

VPC endpoints provide private paths to supported AWS services, such as S3, SSM, and SQS. They reduce the need for public internet routing for those service interactions.

07 · DATA FLOW

Upload to alert, in six stages

01 · Upload

API Gateway and S3

The upload endpoint accepts the request and the CSV is stored in the raw S3 area for processing.

02 · Ingest

ingest.py

The ingestion Lambda reads the file, validates and sanitises rows, and sends invalid records to the quarantine area.

03 · Queue

SQS FIFO

Valid transactions are sent to the FIFO queue. Message groups support ordered processing for the configured account key. A DLQ supports failure isolation.

04 · Score

score.py

The scoring Lambda consumes queued records and applies the three configured risk rules to produce a risk result.

05 · Store

RDS + DynamoDB

Transaction records are persisted in PostgreSQL. Risk scores and event information are written to DynamoDB for the configured lookup patterns.

06 · Alert

alert.py and SES

The alerting component evaluates the risk result and sends the configured email notification for HIGH-risk activity.

Query path

API Gateway → query.py

API Gateway routes supported REST requests to the query Lambda. The handler retrieves information from the database layer and returns the API response.

Reporting path

EventBridge → report.py → S3

EventBridge triggers the monthly reporting Lambda. The reporting process runs the required SQL analytics and writes the generated report files to S3.

The SQS queue is the boundary between ingestion and scoring. If a message repeatedly fails, the dead-letter queue provides a place to isolate it for investigation and controlled recovery.

09 · GOVERNANCE & COST

Governance, retention, and cost awareness

Data governance · POPIA

Classification and lifecycle

  • Personal information: customer identifiers and account-linked transaction details.
  • Operational information: timestamps, transaction types, and processing status.
  • Derived information: risk scores, rule flags, and risk events.
  • Hot tier: RDS PostgreSQL for frequently accessed operational records.
  • Warm tier: S3 storage for less frequently accessed records and analytical outputs.
  • Cold tier: S3 Glacier storage classes for long-term archival where required.
Criterion 5 · Governance

Governance risk register

Risks and AWS controls

  • Unauthorised data access: IAM least privilege, scoped roles, and restrictive resource policies.
  • Credential exposure: SSM Parameter Store, IAM roles, and no hardcoded secrets.
  • Data loss: backups, recovery procedures, and appropriate S3/RDS protection controls.
  • Invalid data: ingestion validation, quarantine storage, and failure handling.
  • Unprotected sensitive data: encryption in transit and at rest, with access restricted to authorised workloads.
Criterion 5 · Criterion 6

Migration strategy

Legacy flat files to AWS

The brief asks for a migration strategy using the 7 Rs and AWS Application Migration Service. For the transaction data workflow, the design considers moving the legacy flat-file process into managed AWS storage and event-driven ingestion. The selected R-classification should be justified in the migration document, with Rehost or Replatform considered against the existing legacy environment.

Retention and compliance

Policy must be validated

The brief specifies hot data in RDS for 12 months, warm data in S3 for 3 years, and cold archival in S3 Glacier for 7 years. This is the proposed capstone lifecycle design. The final retention period must be confirmed against applicable legal and organisational requirements before being treated as a production compliance policy.

Cost management

Designed to minimise unnecessary AWS charges

The capstone architecture is designed around the programme's Free Tier constraints. Lambda, API Gateway, SQS, DynamoDB, S3, and other services have usage-based allowances or pricing. RDS instance hours, storage, data transfer, monitoring, and other usage can still incur charges. The account's Free Tier eligibility, credits, region, and actual consumption must be checked in Billing and Cost Explorer.

NAT Gateway is excluded because it introduces additional hourly and data-processing costs. The project should not be described as guaranteed free simply because it was designed for Free Tier.
